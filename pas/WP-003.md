# WP-003: manual payment uniqueness

Baseline: `develop@19b7ad46c702128a845e4ba19ec7690831022d7b`.
This is a local implementation candidate, not a deployment, migration or cutover.

## Identity evidence

`PAS_CONFIRM_PAYMENT_V1` accepts one optional evidence field:

```json
{
  "receiptEvidence": {
    "receiptCaseId": "synthetic-case",
    "exactHash": "synthetic-exact",
    "visualHash": null,
    "paymentIdentity": {
      "kind": "id",
      "functionVersion": "TARS_RECEIPT_IDENTITY_V1",
      "rawValue": "id:DOC1234567890|2026-09-06|600"
    }
  }
}
```

The envelope and result types are unchanged. Unknown evidence fields, kinds,
versions and malformed values fail validation. Legacy AUTO commands can omit
the new field; MANUAL resolution requires it and returns CONFLICT with
`STABLE_PAYMENT_IDENTITY_REQUIRED` when absent. Old servers reject the extended
evidence rather than silently approving it. There is no compatibility fallback.

The baseline `extractReceiptIdentity` derives, in order, a document/authorization
number, operation ID, receipt number, date-time transaction fingerprint, or text
fingerprint. Its existing output kinds are `id:`, `txn:` and `text:`. The existing
`isStableReceiptIdentity` recognizes those prefixes. The baseline normalizer only
normalizes hour/minute/optional seconds for `txn:`; absent seconds remain distinct
from `:00`. ID/text values remain unchanged. The new PAS representation validates
the existing output grammar before applying that same normalization. It rejects
empty/unknown values rather than interpreting arbitrary message or upload IDs.

Existing raw strings contain date/amount components. These are preserved verbatim
as existing evidence; the caller never constructs a new identity from confirmed
amount/date, strips the existing identifier, or substitutes an upload/case/hash.
Field corrections do not regenerate the identity. No new OCR or business identity
algorithm is introduced. The existing fingerprint's limitations and collisions
are not expanded into a claim of global bank-verified identity.

PAS alone maps `[functionVersion, kind, normalizedRawValue]` into its opaque UUID.
The original raw value and metadata remain in immutable command/evidence records.
Two independent observations with this same stable evidence share one payment;
conflicting values or aliases resolving to different owners hold without mutation.

## Schema and authority

Authority schema version is **3**. `IdentityAlias.kind` adds
`tarsReceiptIdentityV1`; its existing `(kind, aliasValue)` primary key and canonical
FK store the versioned tuple. An insert trigger also prevents REPLACE from
rebinding an immutable alias. Existing UPDATE/DELETE protections remain.
Resolution, creation, command logging and outbox creation stay in the existing
SQLite IMMEDIATE transaction. No process-local identity lookup controls creation.
Versions 1 and 2 are refused without migration; no existing DB is upgraded.

## Manual caller

Private approve (M1), legacy control-room approve (M2), and `/prinyat` (M3) call
`confirmManualReceipt`. Authorization, room scoping and receipt selection still
precede it. Both action dispatchers and the slash executor forward Apps-Engine's
HTTP capability. There is no new in-process authority or native SQLite in TARS.

The full MANUAL/OPERATOR command is persisted before send. The command key is an
observation retry key, not a payment key. Retries, including after response loss
and restart, resend the original command ID, actor, evidence and provenance.
Buttons retain EXTRACTED amount/date provenance; explicit slash arguments are
MANUAL_CORRECTION values with extracted provenance recorded as superseded. The
slash command still selects an existing rejected receipt; it does not edit identity.

The existing caller seam is used without financial callbacks or outbox
acknowledgements. Only a validated CONFIRMED result allows the existing receipt
index projection and its downstream memory/summary/report actions. The projection
carries the PAS canonical ID; matching that opaque ID is projection idempotence,
not identity resolution. ALREADY_CONFIRMED can associate the observation as
`source=duplicate` and never creates a confirmed row or repeats those downstream
actions. This slice does not rebuild missing projections on ALREADY_CONFIRMED.
CONFLICT/REJECTED leave the receipt unconfirmed. Missing configuration, malformed
response, transport failure and timeout fail closed, without a legacy writer.
An index-write failure after a successful authority response is presented as
pending synchronization, not as a claim that PAS rejected or did not count the
payment. Retrying the saved original command repairs a missing local projection;
an already persisted projection does not create another credit on retry.

Existing private accepted-case status repair remains non-authoritative and does
not repeat financial/report actions. A duplicate observation is not marked as a
new accepted ReceiptCase; the operator receives the explicit already-counted
notification. ReceiptCase display delivery and summary delivery remain the
existing best-effort UX, separate from authoritative financial confirmation.

The caller serializes its local index writes. Cross-process financial uniqueness
is enforced in PAS by the stable alias transaction, including when two commands
or callers race. The PAS outbox remains durable and pending: this slice does not
claim consumer completion or introduce a production outbox-draining scheduler.
The existing outbox/inbox reference consumer is unchanged. Production recovery,
outbox consumer installation and live topology are not activated by this patch.

## Transport and configuration

The Apps-Engine adapter uses the existing `PAS_HTTP_V1` operation and validators.
It has no native sockets, service startup, database access or production fallback.
It accepts only the existing isolated service's loopback destination, validates
the response envelope and canonical ID, and bounds calls to two seconds.
The request includes `followRedirects: false` defensively. This is **not** evidence
that an installed Apps-Engine host enforces it: the public
[IHttp interface](https://github.com/RocketChat/Rocket.Chat.Apps-engine/blob/master/src/definition/accessors/IHttp.ts)
does not declare this option, and the inspected public
[server bridge](https://github.com/RocketChat/Rocket.Chat/blob/develop/apps/meteor/app/apps/server/bridges/http.ts)
does not forward it to fetch. Tests prove rejection of returned non-200 responses,
not host-level redirect containment. A verified no-redirect transport/egress policy
is an unresolved prerequisite for any future live activation. No existing runtime
network policy is changed here; the PAS service itself has no redirect response.
Two private optional settings are registered with empty defaults:
`pas_manual_authority_url` and `pas_manual_authority_token` (password). No setting
is populated by this patch. A runtime without configured reachable PAS cannot
manually confirm a payment; manual control remains available for later retry.

No automatic receipt writer is changed, and no historical/legacy credit is seeded
into PAS. Consequently this candidate is not authorization for a mixed live
cutover or evidence of uniqueness against unimported historical credits. Those
remain separate deployment/migration work under the frozen architecture.

## Regression registration

The existing `pas-authority-mvp.test.js` runs
`tests/helpers/wp003-manual-payment.js`. CI file counts remain unchanged. Tests
cover all three real handlers with the real PAS and wire adapter, raw identity
normalization, missing/unsafe evidence, collision/value conflicts, immutable alias
binding, DB-serialized races, retries, lost responses and app restart. The service
suite also executes the Apps-Engine adapter against a separate local PAS process.
UI tests inject deterministic test-only results; they are not the uniqueness proof.
